# Domain Graph compatibility policy

This policy applies to the `domain-graph` package and its serialized graph
format. The current wire format is `domain-graph`, version `1`.

## v1 backward compatibility

Within the `0.1.x` release line, a newer patch release must be able to read
graphs written by `0.1.0` and preserve their graph semantics. The v1 contract
includes the following public shapes and meanings:

- Top-level fields: `format`, `version`, `name`, `schema`, `strict_schema`,
  `nodes`, and `edges`.
- Schema fields: `name`, `entity_types`, and `relations`; relation entries have
  `name` and `hierarchy`.
- Node fields: `id`, `entity_type`, `name`, and `data`.
- Edge fields: `source`, `target`, `relation`, and `data`.

The public names exported from `domain_graph` remain available throughout the
release line. Additive API changes are allowed; removals, renames, or changed
graph/query semantics require an explicit release decision and changelog
entry. Open-world validation by default and opt-in `strict_schema=True` are
part of the current behavior.

## Forward-compatibility limits

The v1 reader accepts `format="domain-graph"` and version `1`. The current
reader also treats omitted `format` or `version` as v1 for legacy input. It
raises `ValueError` for another declared format or version; it does not guess
how a future wire format should be interpreted. Unknown fields in a v1-shaped
payload are not guaranteed to be retained.

Reading a v2 payload is not promised by a v1 reader. Before v2 is introduced,
the project must define an explicit migration, publish its compatibility
rules, add old and new golden fixtures, and test the migration and round-trip
semantics in CI. A version bump must not silently reinterpret v1 data.

## Golden fixtures and equality

Released v1 fixtures are the compatibility baseline. They must be generated by
a released package, checked into `tests/fixtures/v1/`, and treated as
immutable. Compatibility tests must load every fixture and exercise restoration
and representative graph queries on every supported CI Python version.

Compatibility is semantic, not byte-level. Compare `to_dict()` values or
normalized parsed JSON, including node/edge order where order is meaningful to
the current API. Whitespace, indentation, and JSON formatting are not a byte
equality promise; consumers must not compare raw `to_json()` strings.

## JSON data boundary

Node and edge `data` must contain standard JSON-native values: Python `None`,
booleans, finite `int`/`float` values, strings, lists, and dictionaries with
string keys. Convert enums, paths, dates, sets, and other application objects
before adding them to a graph. Non-JSON-native values may raise the underlying
`json.dumps` error and are not part of the wire-format contract.

## Real adapter acceptance contract

An adapter for a real domain is accepted only when it:

1. maps domain symbols to stable strings and declares its schema explicitly;
2. preserves representative source node IDs, entity types, names, edge
   endpoints, relations, and JSON-native data;
3. passes `graph.validate() == ()` in strict mode when using a closed schema;
4. preserves hierarchy, neighbor, ancestor, and descendant semantics, and
   does not introduce hierarchy cycles; and
5. passes `to_dict()`/`from_dict()` and `to_json()`/`from_json()` semantic
   round-trip checks without CoderMind-specific changes to the core package.

The test corpus must include realistic data, unknown-symbol behavior where
relevant, Unicode, nested JSON data, and at least one hierarchy traversal.

## Supported runtime and CI

The package declares Python `>=3.10`, has no runtime dependencies, and lists
Python 3.10, 3.11, and 3.12 classifiers. The current release workflow runs
the standalone tests and packaging checks on Python 3.12. A release claiming
tested compatibility for each supported minor version must add that version
to the CI matrix and run the complete `domain_graph/tests` and golden-fixture
suites there.
